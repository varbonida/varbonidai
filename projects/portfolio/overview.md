# Portfolio Site

Vergel's own project, not client work. See [[people/me|me]].

Personal portfolio site. Its job is to let one visitor decide, in one visit,
whether to hire or interview Vergel. Repo:
`C:\Users\Vergel\Documents\development\portfolio\varbonida`

Progress log: [[projects/portfolio/updates|updates]], which is the same file as
`PROJECT_NOTES.md` in the repo root via a hard link.

## Status

In build. Local dev only, no deployment configured. All content is placeholder.

## Stack

Next.js 16.3.3 (App Router), React 19.2.8, TypeScript, Tailwind 4, Framer
Motion 13, react-icons, npm.

Static throughout: no CMS, no database, no auth, no analytics, no contact-form
backend. Theme toggle, resume download, and contact links all work client-side.

Note for any session working in this repo: `AGENTS.md` warns that this Next.js
version has breaking changes against older training data, and that the guides in
`node_modules/next/dist/docs/` are the reference. That block is regenerated by
`next dev`, so do not try to remove it from a diff.

## Positioning

Two audiences at roughly equal priority: recruiters and hiring managers deciding
whether to interview, and freelance or consulting clients deciding whether to
hire directly. The site must read clearly to both without splitting into two
experiences.

Web development and workflow automation are presented as one skill set, not a
discipline plus a hobby. Separate Automations and Projects sections with equal
top-level billing are themselves the argument, since most developer portfolios
show only one of the two.

Displayed name: "Vergel". Displayed title: "Web Developer | Workflow Automation".

## Design system

`design.md` at the repo root is binding law, not a suggestion. CSS custom
properties switched via `[data-theme]` for dark and light, Inter for body,
Montserrat 700/800 only for headers. New work may compose with those tokens but
must never introduce a competing palette or type scale.

Generated with [[prompts/design-system-doc|Design System Doc]]; the site itself
was scaffolded with [[prompts/portfolio-site-build|Portfolio Site Build]].

## Content

Six clearly-placeholder items each for Projects and Automations, structured so
real content is a data-only swap later. Two standing rules:

- **Never fabricate employers, companies, or client names.** Placeholder entries
  must read as generic rather than as real, unverifiable claims.
- **Do not generate a placeholder `public/resume.pdf`.** The real PDF gets
  dropped in by hand.

## The real blocker

The site is structurally finished and factually empty. Filling it is the only
thing standing between this and a site worth sending to anyone.

The `PRODUCT.md` in the repo says no real case studies exist. That is no longer
true. Three candidates, in order of how easy they are to use:

1. **[[projects/redflagger/overview|Redflagger]]** - live at redflagger.online,
   entirely Vergel's own, nobody's permission needed. A shipped public product
   with a real decision trail: idea selection, stack chosen against AdSense
   constraints, a live dependency risk.
2. **[[projects/mycentimo/overview|MyCentimo]]** - own project, three versions,
   Next.js and Supabase, with genuinely interesting product decisions (guest
   mode, confirm-don't-auto-post recurring transactions). Also nobody's
   permission needed.
3. **[[clients/kelly/dictation-app/overview|Avelisse Dictation App]]** - the
   strongest engineering story: shipped Android alpha, full licence and privacy
   audit, rebrand, a real concurrency bug root-caused and fixed. But it is
   Kelly's product and her brand, so it needs her agreement before any of it
   goes public.

Note what this fixes. The site's whole pitch is that web development and
workflow automation carry equal weight, and the Automations half was the harder
one to evidence. The automation work that exists was done for other people, so
publishing it is a permissions question rather than a writing question. Sort out
what can be shown before designing around it.
